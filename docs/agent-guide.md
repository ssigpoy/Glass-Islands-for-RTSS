# 用 Agent 制作 RTSS OSD

准备一份能正常加载的 `.ovl` 和配套 PNG，再让 Agent 在副本上迭代。可以直接使用本仓库任一主题作为基准。交付时保留独立文件名，让每个版本都能单独加载和回退。

## 1. 给 Agent 一份明确的需求

```text
以我提供的 RTSS OverlayEditor .ovl 和配套 PNG 为基准制作新版 OSD。

目标渲染分辨率为 2560×1440，顶部居中，按 1× 缩放。
使用 Adderley Bold 13 pt，主要读数和单位保持清晰。
显示时间、FPS/帧时间、CPU 和 GPU 的占用、频率、温度、功耗。
请在副本中用固定像素坐标重排。按三位功耗、四位频率、
100% 占用和最长型号留出栏位。保持原监控绑定和现有游戏配置。
图片用透明 RGBA PNG 图集，验证每个 Sprite 的边界。
让警告原位替换时钟。触发条件、刷新和冷却请写清楚。
请交付同目录的 .ovl 和 PNG、静态预览、安装步骤和素材许可。
说明哪些项目已验证，哪些仍需我在游戏里确认。
```

若只想改一处，把范围写成「只改 GPU 底图和强调色」之类的具体目标，避免把排版和诊断逻辑混在一次迭代里。附游戏截图时，保留显示分辨率、字体大小和当前布局文件名。

## 2. 建立最小布局并验证加载

- 用 OverlayEditor 导出一份工作布局，记录 RTSS 和 OverlayEditor 版本、字体及缩放。先确认原生 FPS、一个硬件数据源和一张图片能显示。
- `.ovl` 由 `[Master]`、`[Settings]`、`[General]`、`[SourceN]`、`[LayerN]` 等区段构成。增加或删除项目时同步 `Sources`、`Layers` 和编号。
- 修改 Windows 导出的配置时保留原编码及换行，尤其注意 `°C`、中文字体名和已有的非 ASCII 文本。可按字节替换 ASCII 字段，再用文本编辑器核对。
- 先用原生 `%Framerate%` 和 `%Frametime%`，再从 OverlayEditor 的数据源列表确认 `CPU usage`、`CPU usage max`、`GPU1 usage` 等真实名称。分享给别人时，检查是否带有本机专用的传感器路径。

下面是此项目的静态图层形态。实际布局还需要对应的 `EmbeddedImage` 文件名和正确的图层计数。

```ini
[Layer0]
Name=Time panel
Text=<I=0,0,0,178,38,30>
PositionX=757
PositionY=10
ExtentX=76
ExtentY=30
ExtentOrigin=0
```

## 3. 先按屏幕像素排版，再画素材

这个项目的布局宽 1046 px，在 2560 px 画面上的左边界是 `(2560 - 1046) / 2 = 757`。使用正数像素坐标，便于把布局宽度和字体度量分开。改变字号后重新测最长读数，尤其检查 `100%`、`5888 MHz`、`399 W`、温度和帧时间。数字右对齐、单位固定，能减少位数变化时的横向抖动。

画图时，先按屏幕上的实际尺寸定义轮廓。30 px 高胶囊的半圆半径为 15 px。图集可把横向采样密度减半，再在 RTSS 里拉回显示宽度，但绘制遮罩时仍应按实际横纵比例计算圆角。建议先高倍采样再缩到目标像素，能让小尺寸边缘更平滑。把以下素材装进同一张带 Alpha 的 PNG。

- 普通岛底图和红色警告底图。这个项目用半透明渐变与方向性细边模拟玻璃外观。
- 图标。用 Alpha 图层并在 `.ovl` 里着色，可让多个主题共用同一个素材。
- 进度条的每个状态和警告徽标。固定文字可和图标预先画进同一个 Sprite，用可见像素的边界对齐。

静态图像用 `<I=显示宽,显示高,源X,源Y,源宽,源高>`。上面的例子让显示尺寸由图层范围决定，从图集取 `38 × 30`，在屏幕绘成 `76 × 30`。动态条建议明确写显示尺寸。下面这条来自 GPU 进度条，图集按每行 10 帧排列。

```text
<AI=GPU1 usage,28,8,0,101,0,88,30,8,101,10,0.5,0,0>
```

这里输入 0–100 对应 101 个 Sprite。沿用该配置时，确认 `0`、`50`、`100` 实际选中的帧。黄色徽标也使用同样的动态取图机制，按离散状态选择 Sprite。不要假设超大纹理在所有 RTSS 渲染器中都能正常取图。本项目用 `480 × 424`，发布前逐个检查图块和最后一帧是否越界。

## 4. 把卡顿与持续压力分开

用原生帧时间窗口找短时尖峰，用硬件占用窗口看持续压力。信号质量决定标签可以有多明确。这个项目的红色 `CPU/GPU` 只在尖峰附近观察到占用明显跳升时提供方向，证据不够时用 `SPIKE`。黄色 `CPU/GPU` 表示连续五次采样得到同一倾向。用户可在布局里检查以下源。

| 要改什么 | 查看源 |
| --- | --- |
| 尖峰门槛 | `LagRtssHit` |
| 红色方向推断 | `ShortCpuHint`、`ShortGpuHint` |
| 黄色压力条件和连续样本 | `BnCandidate`、`BnReason` |
| 黄色最长显示和冷却 | `BnCpuState`、`BnGpuState` |
| 警告优先级、时钟复位 | `LagShownReason`、`LagClockVisible` |

此布局按每秒更新一次实现时间状态机，改刷新周期后要重算样本数。RTSS 公式中的 `&&`、`||` 遇到无效值可能传播无效结果，先用 `validate(...)` 和三元条件把输入缺失的情形明确兜底。确认目标版本的 `buf(...,-1)` 与采样顺序后再做状态记忆。 [RTSS 7.3.7 公式更新说明](https://www.guru3d.com/download/rtss-rivatuner-statistics-server-download/)

## 5. 验证和交付

1. **文件检查**。确保 `EmbeddedImage` 与实际 PNG 文件名一致，检查源与图层编号、图块位置、PNG Alpha 及字色。
2. **静态检查**。用一位到四位 FPS、低到满载、三位功耗与缺失温度走一遍。对比 1× 缩放时图标和文字的可见边界。
3. **运行检查**。进游戏观察原生 FPS 是否变化、传感器是否可用、警告能否替换时钟并恢复。用稳定高占用、孤立尖峰、空数据和冷却期间的样本分别验证。静态预览只能说明版式和示例状态。
4. **发布检查**。每个主题提交一对独立命名的 `.ovl` 和 PNG、预览和引用素材的许可证。确认提交里只有公开所需的文件，游戏配置、进程数据和本机路径留在本地。

如果普通岛太实，降低底图填充的 Alpha，图标和数字可保持清晰。实时模糊需要渲染器能读取游戏背景，静态 PNG 提供的是半透明染色和高光。 [Apple-Style RTSS Smoke 主题说明](https://github.com/realHfde/Apple-Style-Inspired-RTSS-Overlay#-why-smoke-replaced-clear)
